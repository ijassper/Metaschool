# Ingrid 디자인 에이전트 운영·인계 지침서

이 문서는 선생님이 디자인 에이전트와 화면을 설계하고, 개발 담당자가 그 결과를 코드 에이전트에 전달해 Ingrid 프로젝트를 이어서 구현할 때 사용합니다. **디자인 완료와 기능 배포 완료는 서로 다른 상태**입니다. 디자인 에이전트의 산출물은 구현 가능한 명세이며, 코드 변경·배포의 최종 책임은 개발 담당자에게 있습니다.

## 1. 역할과 작업 경계

| 담당 | 주된 역할 | 결과물 |
| --- | --- | --- |
| 선생님 | 교육 현장의 문제, 사용자 흐름, 우선순위와 문구 확정 | 요구사항과 디자인 승인 |
| 디자인 에이전트 | 현행 화면 조사, 사용자 흐름·화면·상태·반응형 규칙 설계 | 화면 시안과 이 문서의 인계 명세 |
| 개발자·코드 에이전트 | 기존 코드와 요구사항 비교, 구현 가능성·보안·데이터 영향 검토, 구현·테스트·배포 | 코드 변경과 검증 결과 |

디자인 에이전트는 기본적으로 **운영 저장소를 읽기 전용으로 참고**하고, 운영 서버·학생 데이터·서명키·API 키에 접근하지 않습니다. 운영 DB 조회·수정, APK 빌드·업로드, Git `main` 푸시, 서버 재시작은 디자인 작업에 포함하지 않습니다. 별도 작업 공간에서 Figma 시안이나 독립적인 HTML/CSS 클릭형 프로토타입을 만들 수 있지만, 이를 Ingrid 운영 소스에 직접 병합하지 않고 명세·자산·프로토타입 링크로 인계합니다. 개인정보가 담긴 실제 학생 화면은 전달 전에 이름·학교·답안·서명을 가립니다.

## 2. 작업을 시작할 때 확인할 것

1. 선생님에게 이번 작업의 **화면/사용자/문제/완료 기준**을 한 문단으로 받습니다. 기능 정책이 미정이면 시안을 확정하지 말고 질문으로 분리합니다.
2. 개발자가 제공한 최신 Git 커밋 SHA나 화면 캡처 날짜를 기준선으로 기록합니다. 이전 시안보다 **현재 동작 화면**을 우선합니다.
3. 해당 역할의 실제 진입 경로와 현재 화면을 확인합니다. 교사·학생·최고관리자 화면을 섞지 않습니다.
4. 현재 화면의 필수 요소와 기존 기능을 목록화합니다. 단순히 안 보이도록 처리할 요소와 실제로 삭제할 기능은 구분합니다.
5. 인증, 권한, 저장·제출, 감독, 앱 권한처럼 동작을 바꾸는 제안은 UI 설계와 분리해 **정책 결정 필요**로 표시합니다.

저장소를 볼 수 있다면 [프로젝트 개요](../README.md), `templates/base.html`의 공통 레이아웃·색상, `templates/components/`의 공통 UI를 먼저 확인합니다. 교사 화면은 `templates/activities/`, `templates/accounts/`, `templates/dashboard.html`에, 학생 화면은 `templates/activities/student_*.html`와 `templates/activities/take_test.html`에 주로 있습니다. Android 앱 자체의 네이티브 화면은 `android-student/`에 있으므로 **웹 화면과 앱 네이티브 UI를 혼동하지 않습니다.** 경로는 참고용이며 코드 에이전트가 구현 시 다시 확인합니다.

## 3. 설계 원칙

- 기존 Ingrid 색·컴포넌트를 먼저 재사용합니다. 현재 공통 토큰은 `templates/base.html`의 `--ingrid-primary`, `--ingrid-gradient` 등입니다. 새 토큰은 필요한 이유와 적용 범위를 적습니다.
- 태블릿을 쓰는 학생 화면은 정보 밀도를 높이되, 터치 대상·입력 가독성·스크롤 접근성을 희생하지 않습니다. 데스크톱/태블릿/휴대전화에서 각각 어떻게 줄바꿈·접힘·스크롤되는지 명시합니다.
- 교사 사이드바와 메가메뉴, 학생 화면의 사이드바 유무, 로그인 상태를 고려합니다. 공통 요소를 변경할 때 영향받는 화면을 나열합니다.
- 빈 목록, 로딩, 저장 중, 저장 성공·실패, 권한 없음, 네트워크 끊김, 긴 텍스트, 이미지 없음 등 **화면 상태**를 함께 설계합니다.
- 버튼은 라벨뿐 아니라 눌렀을 때의 결과, 중복 클릭 방지, 취소/뒤로 가기, 실패 시 복구 경로까지 기술합니다. 시안만으로 저장 로직이나 보안 정책이 변경된 것으로 간주하지 않습니다.
- 색만으로 상태를 구분하지 않고 텍스트·아이콘을 병행합니다. 글자 확대, 키보드 포커스, 대비, 이미지 대체 설명을 고려합니다.
- 학생 답안·감독 화면은 일반 카드 페이지보다 보안·자동 저장·제출 상태가 중요합니다. 필수 상태나 종료 경고를 디자인상 제거하려면 개발자와 선생님의 별도 승인 대상으로 표시합니다.
- 화면에 보이는 학년·반·번호·이름, 답안, 감독 영상, 출결 사유·서명 등은 민감 정보입니다. 시안에는 가상 데이터를 사용하고 공개 공유 링크의 접근 권한을 제한합니다.

## 4. 디자인 에이전트에게 붙여 넣을 기본 지침

아래 블록을 새 디자인 에이전트의 기본 지침으로 사용하고, 작업별 요구사항은 별도 메시지로 전달합니다.

> 당신은 Ingrid 학교 교육 플랫폼의 UX/UI 디자인 에이전트입니다. 주요 사용자는 교사, 학생, 최고관리자이며 학생은 Android 태블릿 앱을 자주 사용합니다. 당신의 임무는 실제 현장 요구를 기존 화면과 비교하여 **구현 가능한 디자인 명세와 시안**으로 만드는 것입니다. 기존 동작과 권한을 임의로 변경하지 마세요. 별도 공간에서 클릭형 프로토타입은 만들 수 있지만 Ingrid 운영 코드·DB·서버·서명키는 수정하거나 배포하지 않습니다. 현재 화면을 확인할 수 없으면 추측을 사실로 쓰지 말고 확인이 필요한 항목으로 남기세요. 디자인마다 대상 사용자, 진입 경로, 현재 문제, 변경 전후, 화면 상태, 반응형 동작, 버튼 동작, 정확한 문구, 접근성, 영향 범위, 미확정 정책, 검수 기준을 적으세요. 시안에는 실제 학생 개인정보를 사용하지 마세요. 작업이 끝나면 이 지침서의 **인계 문서 양식**을 빠짐없이 작성해 개발자와 코드 에이전트에게 전달하세요. 디자인 승인과 구현 완료를 혼동하지 마세요.

## 5. 작업별 요청 양식: 선생님 → 디자인 에이전트

```text
작업명:
대상 사용자/기기: (예: 교사 PC / 학생 Android 태블릿)
현재 진입 경로와 캡처:
지금 불편한 점:
반드시 유지할 기능·정보:
원하는 변경:
이번 작업에서 제외할 것:
교사에게 확인해야 할 정책:
우선순위와 희망 완료 기준:
```

작은 수정도 버튼 사이 간격, 표시 문구, 가로·세로 화면처럼 **판단 가능한 값**을 적습니다. 기능 추가·데이터 저장 방식·권한 변경이 필요해 보이면 디자인과 정책 제안을 분리합니다.

## 6. 필수 인계 문서 양식: 디자인 에이전트 → 개발자·코드 에이전트

작업마다 Markdown 문서 한 개를 작성합니다. 파일명 예: `YYYY-MM-DD-화면명-디자인인계.md`. 이미지나 Figma 링크만 보내지 말고 아래 내용을 **문서 안에도 텍스트로** 적습니다. 접근 권한이 필요한 외부 링크는 권한 확인 방법을 함께 남깁니다.

```markdown
# [작업명] 디자인 인계

## 1. 상태·기준선
- 상태: 초안 / 선생님 검토 중 / 디자인 승인
- 작성일·작성자·승인자:
- 참고한 Git 커밋 SHA 또는 화면 캡처 날짜:
- 대상 역할·기기·해상도·진입 경로:
- 관련 시안·이미지·Figma 링크(접근 권한):

## 2. 목적과 범위
- 현재 문제와 현장 사용 사례:
- 이번 변경의 목표:
- 변경 대상 화면·공통 컴포넌트:
- 유지할 기능과 변경 금지 범위:
- 범위 밖의 후속 아이디어:

## 3. 화면별 명세
| 화면/상태 | 현재 | 변경 후 | 정확한 문구 | 조작과 결과 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 예: 학생 답안·저장 실패 | ... | ... | “저장 실패 · 재시도 예정” | 재시도 방법 | 자동 저장은 유지 |

## 4. 레이아웃·시각 규칙
- 데스크톱/태블릿/휴대전화 각각의 배치, 최소 폭, 접힘·스크롤 규칙:
- 크기·간격·색·글꼴·아이콘·이미지 자산(수치와 단위):
- 기존 컴포넌트 재사용 / 새 컴포넌트가 필요한 이유:
- 긴 이름·빈 값·많은 항목·글자 확대 시 처리:

## 5. 상태·상호작용
- 기본 / 로딩 / 빈 상태 / 저장 중 / 성공 / 실패 / 권한 없음 / 오프라인:
- 클릭·터치·키보드·뒤로 가기·취소·중복 클릭의 동작:
- 알림·확인창의 표시 시점, 정확한 문구, 닫힘 조건:

## 6. 구현에 영향을 주는 정책
- 기존 동작으로 확인한 사실(근거 화면 또는 코드 경로):
- 선생님이 확정한 결정(결정일):
- 제안일 뿐 아직 미확정인 사항:
- API·DB·권한·보안·Android 네이티브 변경이 필요해 보이는 부분:

## 7. 검수 기준
- [ ] 역할별 진입/접근이 맞다.
- [ ] 지정한 화면 폭에서 겹침·잘림·불필요한 스크롤이 없다.
- [ ] 필수 상태·문구·버튼 결과가 시안과 같다.
- [ ] 기존 저장·제출·보안·권한 흐름은 유지된다.
- [ ] 미확정 정책은 구현 전 결정됐다.

## 8. 남은 질문·인계 메모
- 개발자가 판단해야 할 기술적 제약:
- 선생님 답변이 필요한 질문:
- 예상 충돌 화면·회귀 확인 대상:
```

디자인 변경이 순수한 색·여백 조정인지, 새 기능·데이터 정책인지 구분해야 합니다. 모호한 요청(예: “저장되게”, “자동 처리”)은 조건·실패 시 동작·기존 데이터 영향이 확인되기 전까지 구현 확정 사항으로 표시하지 않습니다.

## 7. 인수 절차와 완료 기준

1. 선생님이 인계 문서의 화면·문구·정책 결정 항목을 검토하고 **디자인 승인** 상태로 바꿉니다. 미확정 사항은 그대로 표시합니다.
2. 개발자·코드 에이전트가 현재 `main`과 명세를 대조하여 파일·컴포넌트 영향 범위, 기존 기능과의 충돌, 보안·데이터 영향, 테스트 방법을 짧게 회신합니다.
3. 정책 공백이나 큰 기술적 제약이 있으면 임의 구현하지 않고 선생님에게 결정 요청을 보냅니다. 확정된 순수 UI 범위는 독립적으로 구현할 수 있습니다.
4. 코드 에이전트는 구현·테스트 후 변경 화면, 실제 동작, 디자인과 달라진 점, 미완료 항목을 보고합니다. 디자인 에이전트의 시안이 아닌 **실제 앱/웹 화면**으로 선생님이 최종 확인합니다.
5. 개발 담당자가 커밋·푸시·운영 반영·Android APK 배포 여부를 관리합니다. 문서 인계만으로 운영 반영된 것으로 안내하지 않습니다.

인계 문서에 **기준선·화면별 동작·정확한 문구·모든 상태·반응형 규칙·확정/미확정 구분·검수 기준**이 있으면 코드 에이전트가 별도 대화를 몰라도 작업을 시작할 수 있습니다. 이 중 하나가 빠졌다면 필요한 질문을 먼저 하고 해당 부분의 구현을 보류합니다.
